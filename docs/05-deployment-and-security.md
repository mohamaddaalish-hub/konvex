# استقرار، امنیت و توسعه بعدی

## محیط مناسب

این نسخه Next.js/React/TypeScript با SQLite FTS5 است و از دیسک محلی پایدار استفاده می‌کند. برای شروع، یک سرویس Node.js روی VPS یا کانتینر با volume پایدار کافی است. نسخه پشتیبانی‌شده Node.js 22 LTS یا 24 LTS را برای استقرار انتخاب کنید.

**آن را با دیتابیس محلی روی فایل‌سیستم موقت serverless منتشر نکنید.** چند replica هم‌زمان با دیسک‌های جدا، داده‌های متفاوت خواهند داشت. برای چند instance یا ترافیک نوشتاری بالا، مهاجرت repository به PostgreSQL، ذخیره رسانه S3-compatible، محدودسازی توزیع‌شده و صف اعلان لازم است؛ تغییر یک متغیر اتصال به‌تنهایی کافی نیست.

بسته‌های بومی `better-sqlite3` و `sharp` باید روی معماری مقصد نصب شوند. `node_modules` سیستم توسعه را به سرور دیگر کپی نکنید.

## تنظیمات الزامی

```dotenv
ADMIN_PASSWORD=<a-long-unique-secret>
SESSION_SECRET=<at-least-48-random-bytes-encoded-as-base64url>
SITE_URL=https://your-real-domain.example
SITE_INDEXABLE=false
DATABASE_PATH=/persistent/data/konvex.sqlite
```

دامنه بالا صرفاً جای‌نگهدار است. secretها را در secret manager یا فایل با مجوز `0600` نگه دارید، نه Git. مسیر پیش‌فرض رسانه `data/uploads` نسبت به ریشه برنامه است؛ حتی اگر جای دیتابیس را عوض کردید، رسانه را نیز روی فضای پایدار قرار دهید.

پس از تأیید اطلاعات واقعی، فعال کردن ایندکس و راه‌اندازی مجدد سرویس مجاز است. robots و sitemap در runtime تولید می‌شوند. نسخه پیش‌نمایش عمداً از ایندکس مسدود است.

## پشت reverse proxy

- Node روی `0.0.0.0` گوش می‌دهد؛ دسترسی عمومی باید از HTTPS و reverse proxy کنترل‌شده عبور کند.
- پراکسی باید `Host`، `X-Forwarded-Host`، `X-Forwarded-Proto` و IP مبدأ را **خودش تنظیم و ورودی دلخواه کاربر را بازنویسی** کند. اعتماد مستقیم به هدر جعلی، کنترل Origin و rate limit را تضعیف می‌کند.
- درخواست‌های مرورگر از مسیر نسبی `/api/...` استفاده می‌کنند، نه localhost کاربر.
- API، پنل و پاسخ‌های حاوی اطلاعات شخصی را در CDN عمومی cache نکنید. رسانه UUID‌دار را می‌توان cache کرد.
- محدودیت اندازه درخواست و زمان اتصال را در پراکسی نیز اعمال کنید؛ فقط به کنترل برنامه اکتفا نکنید.

نمونه بخش Nginx، پس از تنظیم مستقل گواهی TLS:

```nginx
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $remote_addr;
    client_max_body_size 6m;
    proxy_read_timeout 60s;
}
```

روی ورودی عمومی HTTP، ریدایرکت HTTPS اعمال کنید. HSTS را پس از تأیید پیکربندی TLS فعال کنید. تنظیمات استقرار، DNS، گواهی، CDN و ایمیل در این محیط به حساب واقعی شرکت متصل نشده‌اند.

## کنترل‌های موجود

- ورود مدیر با مقایسه زمان‌ثابت و scrypt، نشست HMAC امضاشده، انقضای هشت‌ساعته و خروج.
- کوکی HttpOnly/SameSite و Secure پشت HTTPS؛ CSRF امضاشده همراه با بررسی Origin و header.
- rate limit پایدار در SQLite؛ محدودیت تلاش ورود، استعلام، جستجو و بارگذاری.
- اعتبارسنجی Zod، پاک‌سازی کنترل‌کاراکتر، کوئری پارامتری، whitelist مرتب‌سازی و مسیر رسانه.
- محدودیت واقعی جریان JSON، حتی بدون Content-Length؛ پاسخ 400/413 به ورودی معیوب/حجیم.
- بارگذاری تصویر فقط با احراز هویت/CSRF؛ محدودیت اندازه و پیکسل، decode/re-encode و نام تصادفی؛ SVG/کد اجرایی رد می‌شود.
- اسناد HTML با escape و JSON-LD با escape `<` تولید می‌شوند.
- جلوگیری از تکرار استعلام با UUID idempotency؛ اطلاعات شخصی فرم به analytics ارسال نمی‌شود.
- هدرهای CSP، nosniff، Referrer-Policy و Permissions-Policy.
- عدم دسترسی وب به رمز، فایل env و SQLite در آزمون مسیرهای خصوصی.

## محدودیت‌های امنیتی که باید دیده شوند

این موارد جایگزین ممیزی امنیتی محیط نهایی نیستند:

- پنل یک مدیر دارد؛ MFA، RBAC/SSO، session revocation مرکزی و audit log کامل موجود نیستند. تغییر secret همه نشست‌های قبلی را نامعتبر می‌کند.
- CSP برای سازگاری bootstrap و پیش‌نمایش، inline script/style را می‌پذیرد. در نسخه نهایی nonce/hash مبتنی بر درخواست و `frame-ancestors` مناسب دامنه واقعی را اضافه و دوباره تست کنید. مسدودسازی iframe در این تحویل عمداً فعال نشده تا پیش‌نمایش کار کند.
- حفاظت ضدبات ساده است: rate limit، honeypot و اعتبارسنجی. WAF/CAPTCHA متناسب با ترافیک واقعی می‌تواند لازم شود.
- رمزگذاری دیسک/بکاپ، برنامه نگهداری PII، پاک‌سازی دوره‌ای رسانه بدون مرجع و پایش لاگ باید در عملیات استقرار تنظیم شوند.
- audit ثبت‌شدهٔ وابستگی‌های runtime: صفر مورد گزارش‌شده. audit کل ابزارها: ۲۰ مورد، شامل ۱۶ متوسط و ۴ بالا در وابستگی‌های توسعه. `npm audit fix` بدون تغییر ناسازگار آن‌ها را رفع نکرد؛ ارتقای عمده/جایگزینی ابزارها باید جداگانه آزمون شود. ابزارهای توسعه و traceها روی runtime عمومی نصب/منتشر نشوند.
- هیچ اسکن خودکاری اثبات نبود آسیب‌پذیری نیست. احراز هویت چندکاربره، مرورگر واقعی و زیرساخت نهایی به بررسی مستقل نیاز دارند.

## پشتیبان‌گیری و بازیابی

`npm run db:backup` یک snapshot سازگار SQLite می‌سازد. کپی صرف فایل `.sqlite` هنگام فعال بودن WAL ممکن است آخرین داده را جا بگذارد. پوشه تصاویر، تنظیمات استقرار و secretها را نیز با سیاست دسترسی جدا پشتیبان بگیرید.

برای بازیابی، سرویس را متوقف، نسخه فعلی را نگه‌داری و بکاپ را جایگزین کنید؛ فایل‌های WAL/SHM مربوط به نسخه قبلی را با دیتابیس بازیابی‌شده مخلوط نکنید. مالکیت فایل و volume را کنترل، سرویس را بالا بیاورید و ورود/جستجو/استعلام را بررسی کنید. این عملیات باید ابتدا روی نسخه غیرعملیاتی تمرین شود.

## مسیر افزودن تجارت

انتشار فعلی کاتالوگ + استعلام است. موجودیت محصول، قیمت اختیاری، وضعیت موجودی و روابط محصول از UI جدا شده‌اند. مراحل بعدی بدون بازطراحی هویت بصری، ولی با توسعه backend و فرایند تجاری:

1. تنوع SKU، قیمت‌نامه B2B، تعداد موجودی و سیاست نمایش قیمت.
2. مشتری/سازمان، نقش خریدار، آدرس‌ها و سطح دسترسی.
3. سبد، quote-to-order، سفارش و ledger رزرو/تغییر موجودی.
4. پرداخت، مالیات، حمل، فاکتور، مرجوعی و آزمون webhooks/idempotency.
5. صف اعلان، CRM/ERP، audit trail و پایش رخداد `purchase` پس از موفقیت واقعی سفارش.

نام رویداد `purchase` رزرو شده است؛ در این نسخه خرید یا رویداد خرید ساختگی ایجاد نمی‌شود.
